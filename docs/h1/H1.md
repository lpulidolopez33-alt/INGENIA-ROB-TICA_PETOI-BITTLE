# 2. Descripción del sistema y contexto operacional

## 2.1 Problema, objetivos y alcance

El robot Petoi Bittle, un cuadrúpedo, solo acepta comandos por puerto
serie y no órdenes de voz. El encargo pide que el robot obedezca órdenes
de voz: en este trabajo, dos órdenes válidas y un tratamiento seguro de
las entradas no reconocidas. El valor buscado es un control por voz
fiable que no mueva el robot sin una orden válida. Este documento cubre
el análisis del problema y la especificación inicial (H1). Quedan fuera
la implementación del software, la selección final de la tecnología de
voz, la integración física y las pruebas de H3 y H4. El OpsCon se
referenciará (REF-02) cuando esté disponible.

## 2.2 Frontera del sistema e interfaces externas

El SoI comprende el módulo de reconocimiento de voz, el módulo de
traducción de órdenes y la comunicación con el robot por puerto serie.
El Bittle físico, el usuario y el entorno acústico son entidades
externas con las que el SoI intercambia flujos.

| Elemento externo | Interacción / interfaz | Dentro o fuera del SoI | Fuente / incertidumbre |
|----|----|----|----|
| Usuario | Emite órdenes de voz y recibe avisos | Fuera | Encargo (REF-01); ESC-01 a ESC-06 |
| Entorno acústico | Ruido de fondo y voz ambiente que llega al micrófono | Fuera | ESC-03, ESC-04; OPEN-05 |
| Módulo de reconocimiento de voz | Recibe audio y entrega texto con su confianza | Dentro | Tecnología pendiente de elegir (OPEN-03) |
| Módulo de traducción de órdenes | Convierte órdenes válidas en skills y descarta entradas no reconocidas | Dentro | Diseño del equipo; REQ-03, REQ-11 |
| Puerto serie | Envía \`ksit\` o \`kup\`; informa del estado de conexión | Dentro (interfaz) | REF-03 (Serial Protocol); REQ-07 |
| Bittle (cuadrúpedo) | Ejecuta skills y movimientos | Fuera | REF-03; modelo pendiente (OPEN-02) |
| Registro de eventos | Guarda cada entrada con su resultado | Dentro | REQ-08 |

## 2.3 Condiciones de operación y restricciones conocidas

| ID | Condición, capacidad o restricción | Procedencia | Estado de conocimiento |
|----|----|----|----|
| CTX-01 | El robot se controla por comandos serie con tokens ASCII, sensibles a mayúsculas. | Petoi Serial Protocol | Documentado |
| CTX-02 | Las skills se invocan con \`k\` seguida del nombre sin sufijo (\`ksit\`, \`kup\`). | Petoi Serial Protocol | Documentado |
| CTX-03 | La API Python requiere Python 3.6 o superior, pyserial 3.5 y el repositorio OpenCat completo. | Petoi Python API | Documentado |
| CTX-04 | La documentación consultada cubre Bittle legacy y Bittle X, no el Bittle X V2, que tiene guía propia. | Petoi Doc Center | Documentado. Modelo del equipo pendiente de comprobar (OPEN-02) |
| CTX-05 | El robot no interpreta voz; el reconocimiento debe resolverse en un módulo independiente. | Deducido de REF-03 | Deducido. Pendiente de validar en H2 |
| CTX-06 | El uso se produce en un entorno con ruido de fondo y a una distancia variable del usuario. | Supuesto del equipo | Pendiente (OPEN-05) |

## 2.4 Investigación técnica de viabilidad

Registrar los hallazgos que condicionan lo que puede especificarse:
capacidades documentadas del cuadrúpedo, alternativas de voz,
posibilidades de conexión e integración, limitaciones y riesgos. No
convertir decisiones de implementación todavía abiertas en requisitos
arbitrarios.

| Cuestión | Alternativas o hallazgo | Evidencia / referencia | Impacto en escenarios o requisitos |
|----|----|----|----|
| Movimientos disponibles | Skills verificadas en la documentación: \`ksit\` (sentarse), \`kup\` (ponerse de pie), \`kbalance\`, marchas \`kwkF\` y \`kwkL\`. | Petoi Serial Protocol; Petoi Python API | Base de ESC-01 y ESC-02; permite fijar las dos órdenes válidas |
| Reconocimiento de voz | No investigado todavía en H1. Se evaluarán las alternativas antes de fijar REQ-05 y REQ-09. | Pendiente | Condiciona el umbral U, la precisión (REQ-09) y la latencia (REQ-10) |
| Integración y programación | Control desde Python mediante pyserial y la librería PetoiRobot. Mind+ ofrece una interfaz gráfica sobre la misma librería. | Petoi Python API | Permite prototipar sin firmware propio |
| Restricciones de comunicación | La documentación advierte de un posible límite en el buffer serie para comandos largos. | Petoi Serial Protocol | No afecta a \`ksit\` ni a \`kup\`; limita la longitud de los comandos encadenados |

## 3.1 Identificación de stakeholders

| ID | Stakeholder / clase | Interés o responsabilidad | Fuentes |

# 4. Necesidades de los stakeholders

Recoger necesidades justificadas por el uso y por las condiciones del
problema. Evitar confundir una necesidad con una tecnología concreta o
con una instrucción de implementación.

| ID | Stakeholder(s) | Necesidad expresada | Origen / escenario | Justificación / prioridad |
|----|----|----|----|----|
| NEC-01 | STK-01 | Necesita que una orden válida produzca el movimiento esperado sin repetirla. | ESC-01, ESC-02; REF-01 | Núcleo del encargo. Prioridad alta (propuesta del equipo). |
| NEC-02 | STK-01 | Necesita que una entrada no reconocida no provoque ningún movimiento. | ESC-03, ESC-04; REF-01 | Evita actuaciones por error. Prioridad alta (propuesta). |

## 4.2 Revisión de cobertura de necesidades

Las necesidades NEC-01 a NEC-05 cubren los escenarios nominales (ESC-01,

identificado necesidades relativas a la voz del usuario ni a la
personalización del sistema; quedan fuera de H1. La prioridad es una
propuesta del equipo pendiente de revisión.

# 5. Requisitos del sistema

El Sistema de Interés (SoI) incluye Bittle, su controladora y
servomotores, el ordenador, el micrófono y la aplicación Python. Los
usuarios, supervisores y el entorno quedan fuera. Se distinguen nueve
tipos de requisitos, cada uno con identificador y vínculo con escenarios
de uso.

**Nota de alcance.** Los valores de rendimiento son objetivos propuestos
pendientes de ensayo. La voz se reproduce inicialmente en el altavoz del
ordenador; no se supone que Bittle original hable por sí mismo. La
parada a través de voz o del programa no sustituye a un procedimiento de
intervención independiente.

## 6.2 Comprobación de cobertura

Escenarios sin necesidades asociadas: ninguno. Necesidades sin requisito
derivado: ninguna. Requisitos sin fuente: ninguno. Requisitos sin método

definido. Omisiones abiertas: la falta del OpsCon (OPEN-01) y de un
colectivo de usuario concreto (OPEN-07).

## 6.3 Enfoque inicial de verificación

Solo con software, sin robot: REQ-01, REQ-02, REQ-03, REQ-05, REQ-06,
REQ-07, REQ-08, REQ-11 y REQ-12, mediante un puerto serie simulado.
Requiere integración de componentes: REQ-04 (aviso al usuario) y REQ-09
(precisión, que depende del micrófono y de la tecnología de voz). Exige
observar el Bittle físico: REQ-10 (latencia) y la confirmación final de
REQ-01 y REQ-02 sobre el robot. Todas estas pruebas están planificadas,
no realizadas.
